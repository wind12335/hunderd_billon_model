## A. autoparallel/ —— 声明式前端 + 编译流水线（1886 行 Python）

### A1. `config.py`（194 行）—— 用户唯一的"词汇表"

```python
class Config:                      # (config.py:14)
    # 模型与数据
    model_path, tokenizer_path
    # 拓扑（不填则自动探测）
    num_nodes: int = 1
    gpus_per_node: int | None      # None → environment.py 探测
    world_size                     # 派生属性 num_nodes × gpus_per_node
    # 搜索空间约束（多机扩展加的字段）
    search_max_world_size: int = 128
    search_max_pp: int = 1
    search_max_ep: int = 1
    master_addr / master_port      # 多机 rendezvous
    # 产物控制
    backend: "MEGATRON" | "PYTORCH"
    run_mode: "PLAN" | "LOWER" | "LAUNCH"
    output_dir
    resolved_world_size() / resolved_gpus_per_node()   # 显式值优先，否则回填默认
```

**角色**：声明式编程的入口——用户只描述"我要训什么、在多大集群上"，**从不**说"TP 设几"。
`resolved_*` 系列方法体现了框架的容错哲学：能探测的不要求填，填了的必须被尊重。

### A2. `decorator.py`（49 行）—— `@parallelize` 门面

```python
def parallelize(config: Config | ParallelPlan):   # (decorator.py:19)
    runtime = AutoParallelRuntime(config)
    runtime.compile()    # PLAN:   探测+搜索 → AutoParallelPlan
    runtime.lower()      # LOWER:  plan → 启动脚本+示例代码
    runtime.launch()     # LAUNCH: 子进程执行（可选）
```

**角色**：库形式 API。装饰在用户的训练函数上，或像 examples 那样直接调用。
注意参数类型是 `Config | ParallelPlan` 二选一——这正是框架的核心契约：
**自动搜索的结果和专家手写的并行方案，是同一种东西（ParallelPlan），走同一条后续链路**。

### A3. `runtime.py`（71 行）—— 三段式状态机

```python
class AutoParallelRuntime:         # (runtime.py:30)
    compile() → AutoParallelPlan   # 状态: PLAN
    lower()   → LoweredProgram     # 状态: LOWER（产物落盘 output_dir）
    launch()  → subprocess         # 状态: LAUNCH（调 launcher.py）
    activate()                     # PLAN 后可直接激活（进程内使用 plan）
```

**角色**：把"编译器"的三段（规划/下放/执行）做成显式状态转移。
好处：`run_mode=PLAN` 可以只做沙盘推演不碰集群；`LOWER` 产物可审查、可版本化、可手动改。

### A4. `compiler.py`（310 行）—— compile_plan() 主流程

```python
def compile_plan(config) -> AutoParallelPlan:          # (compiler.py:110)
    spec     = detect_hf_model(config.model_path)      # ① 模型探测（→detect.py）
    env      = detect_runtime_environment(...)         # ② 环境探测（→environment.py）
    venv     = _build_virtual_environment(config, env) # (compiler.py:22) ③ 虚拟规划环境
    search   = search_parallel_candidates(spec, venv)  # ④ 策略搜索（→search.py）
    if config.parallel_plan:                           # 用户显式给了方案
        search = _build_explicit_search_result(...)    # (compiler.py:68) ⑤ 显式覆盖
        _validate_lowerable_parallel_plan(...)         # (compiler.py:63)   仍需过同一验证
    plan = _build_autoplan(spec, search, ...)          # ⑥ 装配 AutoParallelPlan
```

两个精妙处：

- **③ 虚拟规划环境（cross-compilation）**：搜索时不看真机——`_build_virtual_environment`
  用 `search_max_world_size=128` 等配置构造一个假想集群。这就是为什么 8 卡的开发机上
  能规划出 128 卡的 GLM-4.5-Air 方案（TP8/DP8/PP2/EP8 @24.6GB）。
- **⑤ 显式与自动同构**：手写 ParallelPlan 不走捷径，同样要过
  `_validate_lowerable_parallel_plan` 的校验。保证"搜索结果 ≡ 专家输入"不是口号。

### A5. `lowering.py`（1092 行）—— 产物代码生成

按 `backend` 分两条下放路径：

- **MEGATRON 后端**：委托 megatron_mvp/render.py（见 B6），产出 launch 脚本 + hostfile；
- **PYTORCH 后端**：生成可直接 `python3` 运行的示例脚本（调 tools/run_pytorch_llama_tp_dp.py）。

外加产物登记、输出目录管理、以及把 ParallelPlan 里每层的策略元数据写进脚本头注释
（你在 launch_megatron_plan.sh 头部看到的 `attn=(head_shard,...)` 等就出自这里）。

### A6. `launcher.py`（22 行）/ `types.py`（118 行）

launcher：`launch_lowered_program()` 用 subprocess 跑生成的脚本（run_mode=LAUNCH 用）。
types：`AutoParallelPlan`（spec+search_result+策略视图）、`LoweredProgram`（产物路径集合）。

## B. megatron_mvp/ —— 探测/搜索/渲染中端（~3100 行 Python）

### B1. `types.py`（501 行）—— 全部核心数据结构

| 数据类 | 行号 | 内容 |
|---|---|---|
| `ModelSpec` | :37 | 模型的结构化画像：层数/hidden/heads/kv_heads/ffn/vocab/**is_moe/num_experts/top_k/shared_expert**… |
| `ParallelPlan` | :134 | 一次并行方案：tp/dp/pp/ep、每类模块的切法（attention/mlp/embedding/lm_head）、序列并行开关 |
| `SearchCandidate` | :344 | 搜索空间中的一个点：tp_size + pp_size + ep_size + 预估显存 |
| `SearchResult` | :396 | 排序后的候选全集 + 推荐者 |
| `CoarseIR` | :447 | "粗中间表示"：模型剖面 × 并行方案 → 下放用的结构化描述 |

**ModelSpec 是整个编译器的起点**：后面所有显存公式、候选枚举、Megatron 参数渲染，
都只消费这个数据类，不再回头看 HF config.json。GLM-4.5-Air 的规格 stub
（46 层=1 dense+45 MoE、128 专家 top-8、1 共享专家）就是产出一个 ModelSpec。

### B2. `detect.py`（339 行）—— "眼睛"

```python
def detect_hf_model(path) -> ModelSpec            # (detect.py:57)
    读 config.json → 逐字段映射 → 统一命名口径
def _extract_moe_fields(cfg)                      # (detect.py:134)
    识别 MoE 模型：num_routed_experts/top_k/shared_expert
def _estimate_moe_model_params(spec)              # (detect.py:214)
    MoE 参数量估算：dense 部分 + N_experts × expert_params × (激活比例换算)
def load_model_spec(path)                         # (detect.py:259)
    带缓存的入口；权重文件可缺失（规格模式）
```

**角色**：把任意 HF 格式模型目录"看"成 ModelSpec。探测不到的模型 → 明确报错
（而不是猜一个默认值带病跑）。GLM stub 走的就是"无权重、纯规格"路径。

### B3. `environment.py`（38 行）—— 探测硬件

`detect_runtime_environment()`：torch 可用性、device_count、显存总量、HIP/ROCm 版本。
在 DCU 上走 `torch.version.hip` 分支。**只描述单节点**；跨节点的世界由 Config 或
虚拟环境提供——这是刻意的：探测是"观察"，规划是"想象"，两者分离。

### B4. `search.py`（1319 行）—— "大脑"，最核心的文件

```python
@register_search_strategy("BLOCK_LEVEL_FAST")     # (search.py:189) 注册器模式
def _search_block_level_fast(spec, env) -> SearchResult:   # ~5ms 快速通道

def _valid_tp_sizes(spec, env):                   # (search.py:195) TP 必须整除 attention heads
def _valid_pp_sizes(spec, env):                   # (search.py:209) PP ∈ layers 的因子 ∪ {2,4,8,16}
def _common_parallel_reasons(...)                 # (search.py:376) "标准策略域"的约束集
def _estimate_memory(spec, tp, pp, ep, sp) -> GB  # (search.py:457) 显存模型（见下）
def _build_parallel_plan(spec, tp, pp, ep, ...)   # (search.py:553) 候选 → ParallelPlan
def search_parallel_candidates(spec, env)         # (search.py:1247) 总入口
```

**① 候选枚举**：三层循环 tp × pp × ep，每层过 `_valid_*` 合法性剪枝
（TP 整除头数、PP 整除层数、EP 整除专家数与 dp——GLM 128 专家限制 EP ∈ 1,2,4,...）。

**② 显存模型 `_estimate_memory`（:457）**——决定候选生死的公式：

```
参数      bf16      : params × 2B            （TP/EP 切分后按片计）
梯度      bf16      : params × 2B
Adam 状态 fp32      : params × 12B           （m+v fp32 + master weights fp32）
激活      重计算感知 : ∝ layers × mbs × seq × hidden × ~10 × 0.35(重计算压缩)
                     ÷ tp（TP 切激活） × 0.82（SP 再省）
PP 三段切分: front/mid/back 层组分别估         （首层有 embedding、末层有 lm_head）
```

对每个候选算出"单卡峰值 GB"，过滤掉超 HBM 的，剩下的排序。
昨天 16 卡 Llama-8B 的推荐 TP4/DP4/PP1 @30.64GB、GLM-4.5-Air 的 TP8/DP8/PP2/EP8 @24.6GB
都是这个函数的输出。

**③ 标准策略域 `_common_parallel_reasons`**：搜索只在 Megatron 支持的切法里找——
attention 必须 head_shard、mlp 必须 colrow_shard、embedding 必须 vocab_shard。
这是"务实派自动并行"的关键取舍：**放弃任意切法的理论最优，换取每次搜索结果都真的能跑**。
（对照组：Alpa 类框架搜任意切法，但下放到工业运行时的成功率没有保障。）

**④ 三种策略**（strategy 名可配）：
- `BLOCK_LEVEL_FAST`：规则枚举+剪枝，~5ms（我们一直用的）；
- `HIERARCHICAL`：先节点内后节点间的分层搜索；
- `RL_GUIDED_PPO`（ppo_search.py）：把切分选择建模成序列决策，
  `PlacementController(nn.Module)` 输出切分动作分布，PPO 在线更新——
  用真实/模拟的显存与通信代价当 reward。研究性策略，生产路径用 FAST。

### B5. `ppo_search.py`（467 行）—— RL 搜索分支

`PlacementController`（:67）+ episode 采样 + GAE/PPO 更新。
对学习框架而言可以最后再看：它是 search.py 的**可选替换件**，接口同为
`(spec, env) -> SearchResult`，注册器机制保证即插即用。

### B6. `render.py`（442 行）—— "手"，把方案变成真东西

```python
def select_recommended_candidate(search):    # (render.py:18)  挑最优候选
def build_coarse_ir(spec, plan):             # (render.py:37)  plan → CoarseIR（存 coarse_ir.json）
def build_megatron_config(spec, plan, cfg):  # (render.py:148) → ~60 个 Megatron 完整参数
def build_launch_script(...):                # (render.py:288) → launch_megatron_plan.sh 全文
def write_generation_outputs(...)            # (render.py:379) 落盘 5 个产物
```

`build_megatron_config` 是"翻译官"：ModelSpec + ParallelPlan → Megatron 命令行。
例：`num_query_groups=8`（GQA）、`--swiglu`、`--untie-embeddings`、
`--tensor-model-parallel-size 4`、`--sequence-parallel`……
你在 launch_megatron_plan.sh 里看到的每个参数，都能在 spec/plan 里找到出处——
**生成脚本里没有一个拍脑袋的数字**（这正是"编译器"一词的底气）。

`build_launch_script` 生成的脚本骨架：source 激活脚本 → 环境变量默认值 →
`python3 -m torch.distributed.run --nproc_per_node ${GPUS_PER_NODE} --nnodes ${NNODES} ...` →
全部 Megatron 参数。多机支持 = 脚本从环境变量读 `NNODES/NODE_RANK/MASTER_ADDR`，
**同一份脚本两节点共用**（这正是我们 vcjob 编排能成立的前提）。

## C. tools/ —— 执行层（~2300 行 Python）

### C1. `run_megatron_hygon.py` —— Megatron 入口包装

torchrun spawn 的每个进程跑它。职责：
1. `_resolve_script("Megatron-LM/pretrain_gpt.py")` → 定位上游真实路径；
2. 剥掉 `--rank/--world-size/--dist-url`（torchrun 已用 RANK 环境变量接管，双保险重注入）；
3. 调 bootstrap（见 C2）后 `runpy.run_path()` 同进程执行 pretrain_gpt.py。

### C2. `megatron_hygon_bootstrap.py` —— 海光栈补丁装载（排障最常用）

三步链：**typing 垫片**（上游要 Python≥3.12 的 `typing.override`，集群 3.11 →
`typing.override = typing_extensions.override`）→ **上游源码根**前插 sys.path →
**hcu_megatron 补丁层**导入（88 个补丁注册进 MegatronPatchesManager）。
0 补丁视为装载失败（防"环境里碰巧装了 pip 旧版 dcu_megatron 0.15.0"被误用）。

### C3. `check_megatron_hygon_env.py` —— 环境自检

逐项打印：DTK 版本、torch/HIP、上游源码根、补丁层数、可见卡数。
`run_dual_node_test.sh` 体检阶段与人工排障都用它。

### C4. `run_pytorch_llama_tp_dp.py`（1400 行）—— PYTORCH 后端参考实现

手写的 Llama TP+DP 训练器，**不依赖 Megatron**。核心教学价值：Megatron 帮你做的事，
这里全部摊开在明面上——

| 类 | 行号 | 演示的并行原语 |
|---|---|---|
| `ParallelContext` | :314 | 进程组管理：TP 组/DP 组的划分与 group 句柄 |
| `_CopyToTensorParallelRegion` | :151 | 前向 identity、反向 allreduce（f/g 算子） |
| `_ReduceFromTensorParallelRegion` | :168 | 前向 allreduce、反向 identity |
| `_VocabParallelCrossEntropy` | :184 | 词表切分下的交叉熵（免物化 logits 全量） |
| `RowParallelLinear` / `ColParallelLinear` | :848 | 两种线性层切法（列切输入、行切输出） |
| `HfLlamaAttention` | :885 | 按 head 切 QKV/输出投影 |
| `HfLlamaMlp` | :986 | gate/up 列切 + down 行切（SwiGLU） |
| `HfCheckpointLoader` | :362 | HF 权重名 → 并行布局的映射加载 |
| `HfLlamaForCausalLm` | :1105 | 整机拼装 |

**想真正理解 TP，读这个文件比读 Megatron 快十倍**——同样的 autograd Function，
Megatron 藏在 package 深处，这里按教学顺序摊开。文档 04 讲原理时会引用它。
