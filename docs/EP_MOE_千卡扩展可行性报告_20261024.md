# Autoparallel 框架剖析与「EP 专家并行 + MoE + 千卡」扩展可行性报告

日期：2026-10-24 · 基于仓库 `hunderd_billon_model` 当前代码逐文件核读，所有结论均给出 file:line 证据。

术语约定（首现即解释）：
- **TP**（Tensor Parallel，张量并行）：把单层权重矩阵切开分到多卡。
- **DP**（Data Parallel，数据并行）：各卡跑不同 batch，梯度全归约。
- **PP**（Pipeline Parallel，流水线并行）：把模型按层切成多段，各段在不同卡。
- **EP**（Expert Parallel，专家并行）：MoE（Mixture of Experts，混合专家）模型里把不同路由专家放到不同卡，token 通过 all-to-all（简称 a2a，每卡向每卡直发的集合通信）进出专家。
- **PPO**（Proximal Policy Optimization，近端策略优化）：一种策略梯度强化学习算法。

## 二、核心代码是什么（四件套）

**真正的"大脑"是 search.py 里的四个函数群 + ppo_search.py 的控制器**，其余都是"手眼"：

1. **候选枚举**：`_build_world_size_choices`（search.py:221）生成世界大小序列；`_build_mesh_choices`（:242）展开 TP×DP×PP 网格；`_enumerate_proposals`（:863）叠加 front/mid/back 三段式切分策略。
2. **显存解析模型**：`_estimate_memory`（search.py:457-553）——权重+梯度+Adam 状态+激活四项求和；**已 MoE/EP 感知**：路由专家按 EP×TP 双重切分（:491-494），共享专家仅 TP（:497），稠密层前置进 front 组（:465-472），PP 按 stage 层数比例折减（:505-508），序列并行给 0.82 激活折减（:537-539）。参数量核算 `_estimate_transformer_component_params`（:285-339）支持 head_dim 上采样（GLM-4.5 96 头×128 维 ≠ hidden/heads）。
3. **目标函数**：`_candidate_score`（:614，字典序偏好排序）与 `_candidate_reward`（:653，RL 标量奖励：可下发性 +35、当前环境可行 +120、显存余量、world_size 惩罚 −0.5/卡、gbs 奖励、SP/vocab-shard shaping）。
4. **RL 搜索器**：`ppo_search.py` 的 `PlacementController`（:67，MLP 演员-评论家）+ `_build_decision_nodes`（search.py:936，**当前动作空间只有 {mesh 标签, embedding_policy}**）+ masked categorical 采样（ppo_search.py:87）+ GAE 优势估计（:184）+ PPO 裁剪更新（:264）+ 贪心收敛（:308）。

## 四、扩展到「EP+MoE 预训练/微调 + 千卡」逐项分析

**1. 候选空间规模（千卡会不会搜爆？）——不会。**
1024=2^10，TP/DP/PP/EP 整除约束下组合约数十个；解析式显存估计单次微秒级，逐个枚举完全可行。真正需要 RL 的是「组合 × 三段式策略 × micro-batch × EP」的笛卡尔积与多目标权衡——PPO 框架正是为此设计的载体，只需把 EP 加进决策节点（G1）。

**2. 显存模型——已就位，需补 EP 激活项（G4，约 20 行）。**
专家维 EP×TP 切分、共享专家 TP、稠密层前置、PP 折减、SP 折减全部正确；补 a2a 缓冲 ≈ 2×mbs×seq×hidden×topk×bf16 的解析项即可。

**3. 通信/吞吐模型——最大空白（G2+G3），也是论文创新点所在。**
建议新增独立模块 `megatron_mvp/comm_model.py`（约 200-300 行）：
- 体积公式：TP all-reduce ∝ 2×mbs×seq×hidden×(TP-1)/TP；DP 梯度归约 ∝ 参数量（配 Distributed Optimizer 已渲染，render.py use_distributed_optimizer）；PP P2P ∝ 激活；EP a2a ∝ 2×token×hidden×topk×(1-本地命中率)。
- 分层带宽表：RuntimeEnvironment 增加 `intra_node_bw / inter_node_bw / hierarchy`（可从 nvidia-smi topo / 海光 xGMI 拓扑探测，或配置文件注入）。
- reward 加 `−α·est_time`（估计通信时间）即可让 PPO 直接管"快不快"。
- **验证锚点**：我们手里有 16 卡 RDMA 实测数据（run-9，Phase6 M-sweep 的 wait/wire 报告）可校准跨节点带宽项。

**4. MoE 预训练 vs 微调——框架层无本质差异，模板层两处补充。**
两者在并行策略搜索上同构；差异在：初始化（预训练随机初始化 / 微调走 HF→mcore 转换器，convert_hf_glm_to_mcore.py 已具备思路与键名核验工具）、数据（预训练语料打包 / SFT 对话模板，pack_instruct_data.py 改模板即可复用）、路由热身（预训练建议 aux loss 系数退火 + topk warmup，render 加两个模板变量）。G6 修复后 render 即同时覆盖两种任务。

**5. 千卡编排——机制可行，需加固。**
M4 协商（地址标记文件轮询）天然线性扩展到 128 个 worker；需加固：协商超时与重试（✅ 2026-10-26 已落地：marker 时效闸 + 端口探测，见姊妹文档）、master 单点容错、128 worker 日志聚合、torchrun `--nnodes 128` 的 rendezvous 超时参数（✅ 已在 lowering.py 两个模板加 `--rdzv-conf timeout=2400`）。属工程加固非架构变更。

**6. 权重/检查点——mcore 原生解决。**
dist-ckpt（torch_dist 格式）训练侧 `--load` 自动 reshard 到任意 TP/PP/EP 组合——这正是转换器采用该格式的理由；千卡断点续跑（G7）在 mcore 侧原生支持，render 补 save/interval 策略即可。

## 五、结论

**框架能够实现该目标，且当前完成度分层如下：**

| 级别 | 定义 | 状态 |
|---|---|---|
| **L1 放得下、跑得起** | MoE+EP 计划生成、显存可行、旗标渲染、多机拉起 | ✅ **已达成**（64/128 卡 GLM-4.5-Air 计划实证） |
| **L2 搜得准** | EP 进动作空间 + 通信/吞吐代价模型 + 拓扑输入 | ⬜ 需新增约 400-600 行（G1+G2+G3+G4），架构无需重构 |
| **L3 千卡稳跑** | 分层通信模型校准、编排加固、断点续跑、负载不均感知 | ⬜ 工程加固为主（G5+G7+编排），风险中低 |

分层解耦（探测/建模/搜索/渲染/编排互不依赖接口最小化）是本框架最大的架构资产——四个 gap 全部是"往现有插槽里加内容"，不动骨架。

**建议路线（每步独立可验证）：**
1. render 补 G6 旗标（半小时，128 微调也需要）；
2. EP 进 PPO 决策节点 + reward 扩展（G1，~100 行，用现有 64/128 卡案例做回归）；
3. comm_model.py 解析通信模型 + RuntimeEnvironment 拓扑字段（G2+G3，~300 行，用 run-9 实测校准）；
4. 千卡 dry-run：AUTOPLAN_STANDIN_GPUS 替身规划 1024 卡 + M4 编排演练；
5. 补 EP 激活显存项与负载不均惩罚（G4+G5）。

**风险清单**：① 无通信模型时千卡选型可能给出"放得下但很慢"的方案（缓解：先跑步骤 3 再上千卡）；② 128 worker 协商的共享存储竞态（缓解：标记文件原子写 + 超时重试）；③ 专家负载不均在真实数据上的动态性解析模型无法预知（缓解：训练侧 aux loss + 容量因子兜底，属 mcore 既有机制）。

## 附二：剩余项适配记录（2026-10-24 第二批：G2/G3/G7/MLA）

### G2+G3 通信模型与拓扑感知（新文件 megatron_mvp/comm_model.py，~230 行）

解析式每卡每步通信估算：TP all-reduce（每层 2 次，ring 系数 2(tp-1)/tp）、DP 梯度同步（同 ring 总量）、PP 点对点（时延主导）、EP a2a（topk×(ep-1)/ep 占比，每 MoE 层派发+回收）。四类通信各自判定是否跨节点（G3），选机内/机间带宽折算；带宽/时延/每节点卡数为 `RuntimeEnvironment` 字段，可用 `AUTOPLAN_TOPO_GPUS_PER_NODE / _INTRA_BW_GBPS / _INTER_BW_GBPS / _INTRA_LAT_US / _INTER_LAT_US / _TFLOPS` 覆盖，默认值是占位（BW1000 按 8 卡/节点），待集群实测校准。

接入点：①候选携带 `communication`（search_result.json 可见分项）；②BALANCED 与 THROUGHPUT_FIRST 排序元组末尾加通信毫秒平局裁决（仅在其它键全打平时起作用，64/128/稠密三组回归逐位不变）；③PPO 奖励扣减 `min(8, 每步通信秒)`；④render 出注记行。

**模型自己发现了 EP 的大规模价值**：1024 卡 TP8/DP32/PP4 下，EP=1 每卡持全部专家 → 梯度 13GB 跨机同步 1040ms；EP=16 梯度 2GB（161ms）+ a2a 469ms = 630ms 胜出。512/1024@4096 选型因此从 EP=1 翻到 EP=16（单卡显存 53.75G→8.57G），1024@8192 因 a2a 字节翻倍仍 EP=1——这就是"跨节点带宽 << 机内带宽时专家分片换通信"的解析复现。

### G7 断点续训与滚动保留

按每步墙钟估算（通信+计算，250TFLOPS 占位）推荐存档间隔（目标 1h，钳位 [50,2000] 步），保留间隔恒为 10 倍（满足引擎 `save_retain_interval % save_interval == 0` 校验）；渲染 `--save-interval/--save-retain-interval/--use-dist-ckpt/--async-save`（引擎实证：非保留倍数的上一存档由 checkpointing.py 异步删除；async-save 无 persistent-ckpt-worker 时自动关闭，安全）；`--load` + tracker 即自动续训。单份存档体积按 参数×14B 估算：GLM-4.5-Air ≈1.4TB，Ling 类 124B ≈1.6TB，与方案文档 1.5-1.9TB 一致。声明式前端 `--save-interval` 显式值仍优先，默认改为 None=自动推荐。

### Ling-3.0-flash MLA 兼容（探测/显存/渲染三层就绪）

引擎实证（dev box 上用集群版 parse_args 实测）：`--multi-latent-attention` 是有效标志（静态 grep 看似无定义，实测可直接解析并置位）；`--hybrid-layer-pattern` 含 "D" 反而**不会**打开 MLA；MLA 与 GQA 互斥。适配：detect 从 config 的 `kv_lora_rank` 探测（qk_nope_head_dim→--qk-head-dim，qk_rope_head_dim→--qk-pos-emb-head-dim，v_head_dim→--v-head-dim）；显存模型 attention 按低秩结构（q 下采/上采 + kv 下采/上采 + o 投影）；渲染 `--multi-latent-attention` + 五个维度标志并在 MLA 时抑制 GQA/kv-channels。合成 Ling 规格（288 专家/topk16/MLA）全链路通过：总参估算 124.3B（官方 ~124B），搜索 TP8/DP8/PP1/EP8 38.66G，标志齐全无 GQA 泄漏。**剩余**：Ling 真权重下载后跑一次真转换+冒烟（转换器需按 MLA 权重名扩展，当前转换器只覆盖 GLM 的 GQA 布局）。
