# 03 · 框架全链路串讲：一条命令的完整旅程

> 把 01/02 的模块按**时间顺序**串成一条线。样本：昨天跑通的 SCNet 双机 16 卡
> Llama-3.1-8B 链路测试（worker-0 上那条 `generate` 命令 → rank15 打出 iteration 5/20）。
> 配合《多机启动流程详解.md》食用：那篇讲 Bash 编排层，本篇讲框架本体层。

---

## 0. 全景：八个阶段一张图

```
 ①声明        ②探测        ③搜索          ④下放         ⑤编排
 examples CLI → detect → search(5ms) → render → run_dual_node_test.sh
   Config     ModelSpec   SearchResult   launch.sh     (vcjob协议)
                                                         ↓ 两节点 exec
 ⑥拉起        ⑦装载                ⑧训练
 torchrun  → bootstrap(垫片+88补丁) → Megatron 训练循环
 (16进程)     pretrain_gpt.py        RCCL 5通信域 / loss 11.2→3.0
```

阶段①-④发生在 worker-0 上、**只发生一次**（纯 Python，秒级）；
⑤是 Bash 的舞台（另一篇文档）；⑥-⑧在**两节点 16 个进程里各来一遍**（小时级）。

---

## ① 声明：用户说了什么（也什么都没说）

worker-0 执行的完整命令：

```bash
python3 examples/autoparallel_multinode_train.py \
    --num-nodes 2 --gpus-per-node 8 \
    --model-path model/Llama-3.1-8B \
    --backend MEGATRON --run-mode LOWER \
    --sequence-length 4096 --train-iters 20 \
    --output-dir generated/dual16_llama8b
```

注意这里**没有出现**的词：tensor_parallel、pipeline、dp、sequence_parallel、
micro_batch、ffn 切法、optimizer 类型……全部由后面决定。
声明的信息只有三类：**训什么模型、多大的集群、产出到哪**。

> 对照：直接跑 Megatron 要在命令行里手写 60+ 个参数，写错一个（比如 TP 不整除
> 头数）要到很晚才报错。框架把"知道该设什么"从用户责任变成了编译器责任。

## ② 探测：把模型和环境"看"清楚（毫秒级）

```
detect_hf_model(model/Llama-3.1-8B)
  config.json → ModelSpec{32层, hidden4096, 32头, 8 kv头(GQA), ffn14336,
                          vocab, rope, swiglu, is_moe=False}
detect_runtime_environment()
  → {gpu=8/节点, 64GB HBM, HIP 6.3.26093}
_build_virtual_environment(config)      ← 关键一步
  → 虚拟集群{world_size=16, nodes=2×8}
```

从这一刻起，**后面所有环节只消费 ModelSpec 和虚拟环境**——原始的 HF 配置文件
再也不会被读第二次。这就是"规格化"：把异构输入归一为内部类型。

## ③ 搜索：5 毫秒的决策（BLOCK_LEVEL_FAST）

搜索空间是三层循环 `tp × pp × ep`，但每一步都被剪枝：

```
tp ∈ {1,2,4,8,16}   ∩ 整除 attention heads(32) → {1,2,4,8,16}
                     ∩ ≤ world_size(16)          → {1,2,4,8,16}
pp ∈ layers(32)的因子 ∪ {2,4,8,16} → {1,2,4,8,16,32}
ep: dense 模型 → 恒 1
```

对每个 (tp,pp,ep) 组合：`dp = world_size / (tp×pp×ep)`，再算显存 `_estimate_memory`。
实测输出（可在生成日志里看到候选表）：

| tp | pp | dp | 单卡显存 | 判定 |
|---|---|---|---|---|
| 1 | 1 | 16 | 远超 64GB | ✗ |
| 2 | 1 | 8 | 超 | ✗ |
| **4** | **1** | **4** | **30.64GB** | ✓ 推荐 |
| 8 | 1 | 2 | … | ✓（次优） |
| 16 | 1 | 1 | … | ✓ 但无 DP 冗余 |

为什么 TP4 赢了 TP8？显存都能过，但打分函数还要看通信代价模型：
TP 组内每层有 2 次 allreduce（前向+反向），组越大通信量越大；
TP4/DP4 在显存(30.6GB)与通信之间达到平衡。**这就是"自动并行"四个字的全部内容：
在一个被工程约束圈定的空间里，按可解释的代价模型挑最优点。**

产出 `SearchResult{推荐 TP4 DP4 PP1 + 策略三元组 attn/mlp/embedding 的切法}`，
再 `_build_parallel_plan` 装配成 `ParallelPlan`——从这一刻起它与"专家手写的方案"
在类型上无法区分（同一个 dataclass，同一条后续链路）。

## ④ 下放：从方案到可执行产物（render.py）

```
build_coarse_ir(spec, plan)      → coarse_ir.json          (人可读的中间表示)
build_megatron_config(spec,plan) → 60+ 个 Megatron 参数
    例: spec.num_query_groups=8   → --num-query-groups 8
        spec.swiglu               → --swiglu
        plan.tp=4                 → --tensor-model-parallel-size 4
        plan.sequence_parallel    → --sequence-parallel
build_launch_script(...)         → launch_megatron_plan.sh (88行)
write_generation_outputs(...)    → + smoke脚本 + hostfile + launch_cluster.sh
```

生成脚本的三处细节值得看（都能在 generated/dual16_llama8b/launch_megatron_plan.sh 对上）：

1. **头注释就是审计日志**：`规划推荐: TP=4, DP=4, PP=1`、`搜索耗时: 0.0023 秒`、
   三段式策略——出问题可以反向追溯到搜索结果；
2. **环境变量全部 `${VAR:-default}` 形式**：`NNODES:-2`、`NODE_RANK:-0`……
   这是"一份脚本多机共用"的基础——vcjob 两节点 exec 同一文件，靠环境变量分角色；
3. **`--mock-data --tokenizer-type NullTokenizer`**：链路测试不需要数据集，
   vocab 参数仍必须给（Megatron 要建 embedding）。

## ⑤ 编排：Bash 把两个 pod 组织起来

（本篇只留接口，细节见《多机启动流程详解.md》）

worker-0：体检 → 子模块 → 上面的 ①-④ → 把 IP 写进 JOB_TAG 作用域的标记文件 →
`start_training 0 本机IP`（注入 NNODES/NODE_RANK/MASTER_ADDR/NCCL_SOCKET_IFNAME=eth
→ `exec bash launch_megatron_plan.sh`）。
worker-1：轮询标记(tag 吻合) → 等端口 → `start_training 1 masterIP` → exec 同一份脚本。

**框架与编排的边界在这里**：框架产物是"一份参数化脚本"；
编排层负责"让两个节点带着不同参数同时执行它"。前者不知平台，后者不知并行。

## ⑥ 拉起：torchrun 静态 rendezvous

两节点的 launch 脚本都执行：

```
python3 -m torch.distributed.run --nproc_per_node 8 --nnodes 2 \
    --node_rank ${NODE_RANK} --master_addr ${MASTER_ADDR} --master_port 23456 \
    tools/run_megatron_hygon.py Megatron-LM/pretrain_gpt.py <60+参数>
```

时序：worker-0 的 agent 先到 → 在 23456 起 TCPStore 并**静默等待**（日志上
"启动训练后没动静"就是这个，别慌）→ worker-1 的 agent 到达 → 两 agent 会合 →
**各自同时 spawn 8 个训练进程**。环境变量在每个进程里就位：
`RANK = NODE_RANK×8 + LOCAL_RANK`（worker-1 是 8..15）、`WORLD_SIZE=16`。

## ⑦ 装载：16 个进程各自过一遍 bootstrap

每个进程（不分主从）执行 run_megatron_hygon.py →
`typing 垫片(3.11 补 override)` → `sys.path 前插上游源码根` →
`import hcu_megatron（88 补丁生效）` → `runpy 执行 pretrain_gpt.py`。

这一步的意义：**海光栈 = 上游 Megatron(纯 Python) + 导入期猴子补丁**，
不 fork 上游、不打补丁文件、随上游更新可重放。4 个进程在 worker-0、
12 个在 worker-1——不对，是 8+8；每个都独立走这条链，任何一侧失败都会在
自己的日志里留下补丁层检查的痕迹（"88 patches loaded"）。

## ⑧ 训练：Megatron + RCCL 的一天

```
pretrain_gpt.py main():
  args = parse_args(validate_functions=[...])     ← ④ 生成的 60+ 参数全部进入这里
  initialize_megatron(extra_args_provider, args)   ← init_process_group(env://)
      16 进程在 master TCPStore 上会合建 ProcessGroup(torch.tcp)
  model      = get_model(model_provider, ...)      ← GPT 双层 for 循环构建, TP 切权重
  optimizer  = setup_model_and_optimizer(...)      ← 分布式 Adam(fp32 状态分片)
  data       = build_train_valid_test_datasets_provider  ← mock: 随机 token
  train(...)                                      ← 主循环
      每 iteration: forward → loss → backward → grad allreduce → optimizer.step
```

**通信域构建**（初始化最慢的一步，日志 40 条 Init COMPLETE 的来源）：
world(16) + 4 个 TP 组(每组4进程) + 4 个 DP 组(每组4进程) + embedding 组 ≈ 5 个 comm。
节点内走 P2P/IPC（片间互联），跨节点走 NET/Socket over `eth`——
所以 init 期间会看到两节点各 40 条 Init COMPLETE 成对出现。

**训练循环内的分布式动作**（每 iteration）：
1. DP 各副本拿不同 micro-batch，前向各自算；
2. TP 组内：每层 attention/mlp 有 2 次 allreduce（f/g 算子）；
3. backward 后 **DP 组梯度 allreduce（跨节点 TCP）**；
4. 分布式优化器：每张卡只持有 1/dp 的优化器状态分片更新，再 allgather 回权重。

实测（run-7）：285 s/迭代（含 NCCL_DEBUG=INFO 刷屏开销）、loss 11.20→3.03、
显存 34-35%（allocated 17.7GB/卡）。数字不重要，**形态**重要：
iteration 稳定推进 = 拉起/通信/训练三层全部健康。

## 复用视角：换模型/换集群时，哪些层不用动？

| 要换的东西 | 只需改哪里 | 其他层 |
|---|---|---|
| 换 dense 模型（Llama→Qwen） | `--model-path` 指向新目录（detect 自动认） | 全部自动适配 |
| 换 MoE 模型（GLM-4.5-Air） | 换 model 目录 + `--search-max-pp/--search-max-ep` 放开 | detect 提取 MoE 字段→ search 搜 EP → render 生成 MoE 参数 |
| 卡数 16→128 | `--num-nodes 16` | 虚拟环境照常 cross-compile；编排层需泛化（M4） |
| 只想要方案不要脚本 | `--run-mode PLAN` | 在 compile 后停住 |
| 专家手写方案 | `--explicit-plan plan.json` | 与自动方案走同一验证/下放链 |

这张表就是框架的"用户故事"。下一篇（04）转入原理层：模型内部到底在算什么。
