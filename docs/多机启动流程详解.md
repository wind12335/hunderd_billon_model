# 千卡模型多机训练启动流程详解

> 以 SCNet 双机 16 卡（2 节点 × 8 × BW1000 DCU）Llama-3.1-8B 链路测试为样本，
> 完整拆解 `scripts/run_dual_node_test.sh` 从被执行到打出第一个 `iteration ... loss=` 的全过程。
> 适用于组会汇报与新人接手。写作基线：2026-10-07 已跑通的版本（iteration 正常推进、loss 收敛）。

---

## 0. 一页总览

**目标**：在没有 SSH、没有调度协调的 K8s vcjob 平台上，把同一个训练作业在 2 个对等 pod 上拉起，
并让 16 个训练进程完成分布式握手、建好全部通信域、跑起训练循环。

**核心难点**：平台在两个 pod 上**同时、对等地**执行同一份启动脚本——没有人告诉任何一个 pod
"你是主节点还是从节点"、主节点 IP 是多少。单机训练里天然成立的前提（`MASTER_ADDR=127.0.0.1`、
"先起进程再握手"），在多机上全部变成需要显式解决的问题。

**我们的答案是一个五层结构**：

| 层 | 解决的问题 | 载体 |
|---|---|---|
| L0 编排自举 | 脚本自身可靠启动、失败可见 | 心跳行 / ERR trap / 挂载重试 |
| L1 地址协商 | "谁是 master" | 共享存储标记文件（作业级隔离） |
| L2 分布式会合 | 两边到齐才发车 | torchrun 静态 rendezvous（TCPStore） |
| L3 环境适配 | 海光 DCU 栈 + Megatron 源码补丁链 | bootstrap（typing 垫片 + hcu_megatron 补丁层） |
| L4 训练本体 | 通信域构建 + 前向反向 | Megatron + RCCL（TP/DP 集合通信） |

## 1. 背景：平台约束与框架目标

### 1.1 SCNet vcjob 执行模型（一切设计的出发点）

- 平台把启动脚本 **staging 到 `/`**，用 **`/bin/sh` 在两个 worker pod 上各执行一次**，无参数；
- pod 之间**没有 SSH**，只有 K8s 集群网络（pod IP 可达，headless DNS 可解析 FQDN）；
- 两个 pod **共享挂载**同一块存储（`/root/private_data/thousand_model`），且该存储**跨作业持久**；
- pod 名形如 `vcjob-<id>-<hash>-worker-0` / `...-worker-1`，**同一作业的两个 pod 共享 `-worker-N` 之前的前缀**；
- 平台日志经管道收集，**stderr 疑似不被采集**（这是多个防御设计的直接原因）。

### 1.2 框架侧

autoparallel 框架的分工：**搜索规划**（TP/DP/PP/EP 划分、显存预估）→ **下放生成**
（产出可直接执行的 launch 脚本）→ **启动执行**（本脚本负责的平台适配层）。
多机与单机在"搜索"环节完全同构（搜索器只看 world_size，不关心 1×8 还是 2×8），
差异全部集中在"启动执行"层。

## 3. 逐阶段详解

### 阶段 A：脚本自举与"防静默死"（`run_dual_node_test.sh:20-53`）

```bash
if [ -z "${BASH_VERSION:-}" ]; then exec bash "$0" "$@"; fi   # /bin/sh → bash
printf '[dual-test] 脚本已启动 hostname=%s bash=%s\n' ...      # 心跳行
set -euo pipefail
trap '... 第 %s 行以退出码 %s 终止 ...' ERR                     # 失败现场打印行号
```

四个部件各自对应一次真实事故：

| 部件 | 为什么存在 |
|---|---|
| bash 重切 | 平台用 `/bin/sh`（dash）调起，脚本用了 bash 特性（`BASH_REMATCH`、`[[ ]]`） |
| **心跳行** | 平台日志若连这行都没有 → 脚本根本没被执行（pod/暂存问题），与脚本内容无关。这是"脚本问题 vs 平台问题"的**分界线** |
| `set -euo pipefail` | 任何未捕获失败立即退出，不带病运行 |
| **ERR trap** | `set -e` 的退出是**静默的**（退出码有了、输出没有）。trap 把失败行号+退出码打到 stdout。直接动因：某版本网卡探测行在无 `iproute2` 的镜像里以 127 静默退出，worker-0 "零日志" |

另一个细节：`die()` 同时写 stdout+stderr（`tee /dev/stderr`）——因为平台日志疑似不收 stderr，
只写 stderr 的报错等于没报。

### 阶段 B：环境探测（`detect_repo_root` / `is_vcjob`，`:88-146`）

**仓库根探测**：脚本被 staging 到 `/` 执行，不能依赖 `$0` 的路径。按优先级尝试：
环境变量 `THOUSAND_MODEL_ROOT` → 脚本所在目录 → 常见挂载点，
判据是"存在 `tools/launch_cluster.py` 且存在 `megatron_mvp/search.py`"（防误认任意目录）。

**120 秒挂载重试**：共享存储挂载偶发晚于容器启动（本平台两次复现）。
找不到就每 10 秒重试、最多 120 秒，而不是立即 die。
（重试期间会打印"共享存储暂不可见"——不是报错，是等挂载。）

**平台识别与角色提取**：

```bash
[[ "$h" =~ ^(.*)-worker-([0-9]+)$ ]] || return 1
JOB_TAG="${BASH_REMATCH[1]}"    # 例: vcjob-2107...-abc12335-66689
ROLE="${BASH_REMATCH[2]}"       # 0 或 1
ADDR_MARKER="${OUT_DIR}/.vcjob_master_addr.${JOB_TAG}"
```

hostname 匹配 `-worker-N` → 判定在 vcjob 里；**JOB_TAG（pod 名公共前缀）是"同一作业"的唯一标识**，
它决定了地址标记文件的名字。识别失败则落入裸机 SSH 模式（同一份脚本的另一条路径，
组会可略）。**这就是"角色"的来源：没有调度器告诉我们，我们从 pod 名里自己解析。**

### 阶段 C：worker-0（主节点）流程（`vcjob_main` case 0，`:221-231`）

```
体检 → 子模块 → 规划生成 → 清理+发布地址 → 以 NODE_RANK=0 启动训练
```

1. **体检**（`local_preflight`）：`python3 -c 'import torch'` 能否跑通并看到 8 张卡；
   模型目录在位。**只查本机**——多机下任何一台体检失败都应尽早死，而不是拉起一半。
2. **子模块确认**（`ensure_submodules`）：Megatron 上游源码在
   `Megatron-LM-das/3rdparty/Megatron-LM`（git submodule）。缺失则尝试自动 `git submodule update`
   （需要 GitHub 可达），失败给出人工处理指引。
3. **规划与生成**（`generate`）——框架的真正入口：

   ```bash
   python3 examples/autoparallel_multinode_train.py \
       --num-nodes 2 --gpus-per-node 8 --model-path model/Llama-3.1-8B \
       --backend MEGATRON --run-mode LOWER \
       --sequence-length 4096 --train-iters 20 --output-dir $OUT_DIR
   ```

   搜索器输出并行方案（本轮：**TP=4, DP=4, PP=1, world_size=16, 序列并行 on，
   预估单卡显存 30.64GB/64GB**），并把方案"下放"成可执行产物：
   `launch_megatron_plan.sh`（多机训练入口）、`launch_megatron_smoke.sh`（单机冒烟）、
   `hostfile`、`launch_cluster.sh`（SSH 模式一键拉起）。

   **硬校验**：`grep -q "world_size=16"`——搜索结果若与 2×8 的拓扑不符（历史上有过
   拓扑错配 bug），宁可终止也不带着错误 world_size 去连别的节点。

4. **发布地址**（标记协议，详见下节）。
5. `start_training 0 <本机IP>`。

### 阶段 D：worker-1（从节点）流程（case 1，`:232-256`）

```
等标记文件(tag吻合) → 校验生成脚本可见 → 体检 → 等端口开放 → 以 NODE_RANK=1 启动
```

三个等待各有一次"从节点视角"的有序退避，每个都有独立超时（15 分钟）与明确报错指引。

**地址协商协议**（本脚本最核心的自研机制）：

```
worker-0 写:  printf 'JOB_TAG IP' > marker.tmp && mv marker.tmp marker   # 原子写
worker-1 读:  tag 吻合才采用，否则继续等
```

三条设计原则，每条对应一次踩坑：

| 设计 | 防的事故 |
|---|---|
| **tmp+mv 原子写** | worker-1 可能读到写了一半的文件（拿到半个 IP） |
| **文件名带 JOB_TAG + 内容首字段校验** | 共享存储跨作业持久：上一作业的 worker-1 曾直接 `cat` 到**已销毁 pod 的 IP**（.196），然后花 15 分钟等一个永远不会开放的端口；而真正的 master（.207）在 rendezvous 里等它，双方互等至超时 |
| **worker-0 发布前 `rm` 全部历史标记** | 旧标记无限累积 |

（协议成立的前提：共享存储对两个 pod 同时可见——这正是它比环境变量/DNS 更适合当信箱的原因。）

**端口探测**：`/dev/tcp/${master}/${port}` 每 5 秒一次。端口开放 = torchrun agent 已就位。
超时后仍尝试启动（宁可让 torchrun 报错，也不放弃）。

### 阶段 E：`start_training`——环境注入清单（`:188-214`）

这一步把"平台约定的角色"翻译成"分布式训练的标准环境变量"：

| 变量 | 值/来源 | 作用 |
|---|---|---|
| `NNODES / NODE_RANK` | 2 / 0或1 | torchrun 静态模式的节点数与本节点序号 |
| `MASTER_ADDR / MASTER_PORT` | worker-0 的 IP / 23456 | rendezvous 地址（**两边必须一致**——来源即标记文件） |
| `GPUS_PER_NODE` | 8 | 本节点进程数 |
| `PYTHONUNBUFFERED=1` | 固定 | 平台日志是管道收集，python 默认块缓冲会让日志滞后到进程退出 |
| `NCCL_SOCKET_IFNAME` | 自动探测默认路由出接口（回退 eth0） | 把 RCCL 跨节点 socket 绑定到容器主网卡，避免 FQDN 多地址解析导致连接被 reset。注：实际探测到的名字是 `eth`——所以不能硬编码 |
| `NCCL_DEBUG` | 默认 WARN（可覆盖） | 镜像默认 INFO 每节点刷几千行；链路验证完成后降级，排障时改回 |
| `DIST_TIMEOUT_MIN` | 默认 20 | 集合通信超时（分钟）。任何一侧死掉，另一侧 20 分钟内报错退出，而不是永远挂起 |

最后 `exec bash "$PLAN_SCRIPT"`——**exec 替换进程**，脚本进程即训练进程（PID 不变，
信号直达，不留中间壳）。

> 工程细节：探测网卡的命令替换内置 `|| true`——因为 `set -euo pipefail` 下，
> 镜像里没有 `ip` 命令时管道返回 127 会**静默杀死整个脚本**（真实事故）。

### 阶段 F：生成的 launch 脚本内部（`generated/dual16_llama8b/launch_megatron_plan.sh`）

两节点执行的是**同一份**文件（共享存储），仅靠环境变量区分角色：

```bash
source scripts/activate_megatron_hygon.sh      # DTK 环境 + PYTHONPATH + 上游根
export NNODES="${NNODES:-2}" NODE_RANK=... WORLD_SIZE=$((NNODES*GPUS_PER_NODE))
python3 -m torch.distributed.run \
    --nproc_per_node 8 --nnodes 2 --node_rank ${NODE_RANK} \
    --master_addr ${MASTER_ADDR} --master_port ${MASTER_PORT} \
    tools/run_megatron_hygon.py Megatron-LM/pretrain_gpt.py \
    --tensor-model-parallel-size 4 --pipeline-model-parallel-size 1 \
    --sequence-parallel --bf16 --use-distributed-optimizer ... \
    --mock-data --tokenizer-type NullTokenizer --vocab-size 32000
```

要点：并行参数就是阶段 C 搜索结果的直接体现；`--mock-data + NullTokenizer`
意味着**不需要任何数据集**——链路测试验证的是通信与启动，loss 数值无意义但必须有限且大致下降。

### 阶段 G：Python 侧 bootstrap（`tools/run_megatron_hygon.py` → `megatron_hygon_bootstrap.py`）

每个训练进程（共 16 个）在进 Megatron 之前都要过这一关：

```
run_megatron_hygon.py
 ├─ _resolve_script: Megatron-LM/pretrain_gpt.py → Megatron-LM-das/3rdparty/.../pretrain_gpt.py
 ├─ 剥掉 --rank/--world-size/--dist-url（torchrun 已用环境变量接管）
 ├─ bootstrap():
 │   ├─ typing 垫片: 上游 requires-python>=3.12（hybrid.py 用 typing.override），
 │   │   集群是 3.11 → typing.override = typing_extensions.override   ← 拦截所有进程的崩溃
 │   ├─ 解析上游源码根 → sys.path 前插（MEGATRON_UPSTREAM_ROOT 优先）
 │   └─ 加载海光补丁层: Megatron-LM-das/hcu_megatron 源码导入即打补丁
 │      （88 个补丁注册进 MegatronPatchesManager；0 补丁视为失败）
 └─ runpy.run_path(pretrain_gpt.py, run_name="__main__")   ← 同进程内执行，无二次 fork
```

为什么值得汇报：海光版 Megatron 是"上游 0.18.2 + 导入期补丁"的二层结构，
pip 里还有个**不配套**的旧版 `dcu_megatron 0.15.0`（接口对不上）。我们把补丁层解析固定为
"**版本配套的源码层优先**"，并且加了**补丁数非零的自检**——这两个决定消掉了整类
"环境里碰巧装了什么就用什么"的随机故障。

### 阶段 H：分布式初始化与训练循环（Megatron 内部，简述）

1. `init_process_group`：16 个进程凭 `RANK/WORLD_SIZE/MASTER_ADDR/MASTER_PORT` 环境变量
   在 master 的 TCPStore 上完成进程组初始化（RANK = NODE_RANK×8 + LOCAL_RANK，
   所以 worker-1 是 8~15）；
2. 按全局 rank 切分 TP/DP 组，**逐个建 NCCL/RCCL 通信域**：world(16) + 4 个 TP 组 +
   4 个 DP 组 + embedding 组 ≈ 5 个 comm × 8 进程 = **40 条 `Init COMPLETE`**；
   节点内走 P2P/IPC，**跨节点走 NET/Socket（TCP）**——这是多机与单机在通信层的本质差异；
3. 构建 GPT 模型（TP=4 切权重 + 序列并行），mock 数据器供数；
4. 训练循环：每 iteration 前向/反向后做 **DP 梯度 allreduce（跨节点）** + 分布式优化器分片更新。
   进度行由 `print_rank_last` 打印 → rank 15 在 worker-1 → **带时间戳的 iteration 行只在
   worker-1 日志出现，worker-0 是显存报告**（不要误判主节点没在跑）。

## 4. 多机 vs 单机：新增步骤对照

| 环节 | 单机 8 卡 | 多机 2×8（本方案新增） |
|---|---|---|
| 谁是 master | 不存在该问题（127.0.0.1） | **共享存储标记文件协议**（JOB_TAG 隔离 + 原子写 + tag 校验） |
| 进程拉起时机 | 立即 | **torchrun 静态 rendezvous**：两 agent 会合才同时 spawn（master 等待期静默是正常的） |
| rank 编号 | RANK=LOCAL_RANK=0..7 | RANK=NODE_RANK×8+LOCAL_RANK（worker-1=8..15），WORLD_SIZE=16 |
| 通信域 | 纯节点内 P2P/IPC | 增加跨节点 **NET/Socket 通道** + 每 rank 一个 proxy 线程 + proxy 间 TCP 连接；拓扑探测/树形算法/32 通道协商，init 耗时数分钟 |
| 集合通信代价 | 片间互联（µs 级） | 每 iteration 的 DP allreduce 跨 TCP（ms 级），节点间持续网络流量 |
| 容错 | 单点，失败即退 | `DIST_TIMEOUT_MIN`：一侧死亡，另一侧限时退出而非永挂 |
| 日志可见性 | 本地终端 | 管道收集：需 `PYTHONUNBUFFERED`、心跳行、stdout 兜底的 die、ERR trap |

## 5. 验证结果（2026-10-07 运行）

| 指标 | 数值 |
|---|---|
| 通信域 | 两节点各 `Init COMPLETE ×40`（5 comm × 8 进程，全部成功） |
| 训练 | `iteration 5/20` 持续推进，loss 11.20 → 8.43 → 3.52 → 3.88 → 3.03（随机初始化下的正常形态） |
| 显存 | 16 卡全部 34-35%（allocated ≈17.7GB，reserved ≈19.5GB/卡） |
| 节奏 | ≈285 s/迭代（含 NCCL_DEBUG=INFO 海量日志与小 batch 开销，非真实性能） |
| 错误 | 两节点 0 Traceback |

日志中的已知噪音（不是错误）：
- `socketProgress: Connection closed by remote peer`（WARN，多 comm×多通道建连时重复连接被对端正常关闭；出现的同时 40/40 Init COMPLETE 全部达成）；
- `NUMA auto balancing enabled`（性能建议，可在节点上 `sysctl kernel.numa_balancing=0`）。

## 6. 设计决策一览（组会工程亮点）

每个防御机制都能回答"防的是什么"：

1. **心跳行** —— 区分"脚本没被执行"与"脚本执行失败"；
2. **ERR trap + die 双写 stdout** —— 对冲平台不收 stderr 的"静默死"；
3. **挂载 120s 重试** —— 共享存储晚于容器就绪（两次复现）；
4. **JOB_TAG 作用域标记 + tag 校验 + 原子写 + 发布前清理** —— 跨作业残留读到死 IP；
5. **world_size=16 硬校验** —— 搜索/拓扑错配不带病上线；
6. **NCCL_SOCKET_IFNAME 自动探测**（且必须 `|| true` 兜底）—— FQDN 多地址 + 镜像无 iproute2；
7. **DIST_TIMEOUT_MIN=20** —— 半死作业限时退出；
8. **补丁层版本固定 + 补丁数自检** —— 消除"环境里碰巧装了旧版补丁包"的随机性。

## 7. 当前边界与下一步

本脚本目前是**链路测试入口**（mock 数据、20 步、双机）。到 GLM-4.5-Air-105B 128 卡全量微调还需：

- M2 checkpoint 保存/断点恢复专项验证（本轮 `save-interval=1000 > train-iters=20`，保存未触发；Hygon 栈保存有 segfault 前科）；
- M3 GLM45Bridge 模型路由（MoE/EP）+ 真实 tokenizer（vocab 151552）与数据管线 + HF→Megatron 权重转换；
- M4 编排泛化到 16 worker（`NODE_RANK=$ROLE` 直接推广）→ 32 卡 → 128 卡（TP8/DP8/PP2/EP8，预估 24.6GB/卡）；
- 性能：NCCL_DEBUG 已降 WARN，NUMA balancing 可关，吞吐验收标准待定。
