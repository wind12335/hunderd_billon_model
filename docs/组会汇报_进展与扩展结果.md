# 组会汇报 · 精简版：多机扩展进展与结果

> 5 分钟讲完版。详细依据见 `多机启动流程详解.md`（编排细节）与 `01-04` 系列文档（框架与训练原理）。

---

## 1. 背景一句话

在已有单机自动并行框架（声明式配置 → 自动搜索 TP/DP/PP → 生成 Megatron 启动脚本）基础上，
本次工作将其**扩展到多机多节点**，并最终目标指向 GLM-4.5-Air-105B 的 128 卡全量微调。

## 2. 本次做的扩展（三层，代码全部落地）

| 层 | 改动 | 效果 |
|---|---|---|
| **搜索层** | Config 增加 `num_nodes / gpus_per_node / search_max_pp / search_max_ep`；虚拟规划环境支持 cross-compile（8 卡开发机上可规划 128 卡方案） | 搜索器只看 world_size，单机多机完全同构，无需改搜索算法本身 |
| **生成层** | launch 脚本参数化（`NNODES / NODE_RANK / MASTER_ADDR` 环境变量驱动）；新增 hostfile 与 `launch_cluster.py`（SSH 多机一键拉起） | **同一份生成脚本，多节点共用**，仅靠环境变量区分角色 |
| **编排层** | 新写 `run_dual_node_test.sh`：SCNet vcjob 平台自适应（无 SSH、无调度协调、两 pod 对等执行同一脚本） | 角色自识别 + 共享存储地址协商 + 全链路容错 |

编排层的核心自研机制（因为没有现成方案可用）：pod 主机名解析出 `worker-0/1` 角色；
主节点把 IP 写入**作业隔离（JOB_TAG 作用域）的共享存储标记文件**（原子写+标签校验），
从节点轮询读取后双方以 torchrun 静态 rendezvous 会合。

## 3. 扩展结果：双机 16 卡链路测试已跑通（SCNet，2×8 BW1000 DCU）

| 指标 | 结果 |
|---|---|
| 并行方案（自动搜索，耗时 0.0023s） | TP=4, DP=4, PP=1，序列并行，world_size=16 |
| 显存预估 vs 实测 | 预估 30.64GB/卡（含优化器余量）；实测 allocated ≈17.7GB、占用 34-35% |
| 分布式初始化 | 两节点各 40 条 `Init COMPLETE`（5 个通信域 × 8 进程，全部成功） |
| 训练 | iteration 稳定推进，loss 11.20 → 3.03（随机初始化+mock 数据的正常形态） |
| 稳定性 | 两节点 0 Traceback |

结论：**多机 rendezvous、跨节点 RCCL 通信、自动搜索→生成→编排的完整链路全部验证通过**。

## 4. 过程中解决的典型问题（各一行）

| 问题 | 解法 |
|---|---|
| 跨作业地址竞态：从节点读到上一作业残留的死 IP，双方互等至超时 | 标记文件按 JOB_TAG 命名 + 内容标签校验 + 原子写 |
| 主节点"零日志静默死"（平台不收 stderr + 挂载晚于启动 + `set -e` 静默退出） | 心跳行 + ERR trap 报行号 + 120s 挂载重试 + die 双写 stdout |
| 跨节点连接被 reset / WARN 风暴 | `NCCL_SOCKET_IFNAME` 自动绑定容器主网卡（实测名 `eth`，不能硬编码）；日志降噪至 WARN（已验证 WARN 为良性） |

## 5. 下一步（到 105B 全量微调的路线）

1. **M2** checkpoint 保存/断点恢复专项验证（当前 `save-interval > train-iters`，保存路径未真实触发）；
2. **M3** GLM-4.5-Air 模型路由（MoE/EP + 真 tokenizer/数据 + 权重转换）；
3. **M4** 编排泛化到 16 worker（`NODE_RANK=角色号` 直接推广）→ 32 卡 → **128 卡**。

128 卡方案（框架已 cross-compile 出）：TP=8 / DP=8 / PP=2 / EP=8，预估 24.6GB/卡（64GB HBM）。
